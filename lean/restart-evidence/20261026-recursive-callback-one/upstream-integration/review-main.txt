Memo key completeness

edgeCopiesWith is a pure function of original, childParts, wanted parts, unwanted parts, root symbol and the full ordered child-shape list. The memo key contains exactly the four varying arguments. original and childrenOf are fixed in the refine closure. The call passes wanted' and nubOrd unwanted exactly as the old direct call did. It keeps shape order and duplicates. It performs no new sorting, canonicalization, template filtering or split pruning.

Edge identity, constraint and full child-node identities are correctly absent from the key. edgeCopiesWith does not inspect them. The caller still applies the returned obligation lists to each actual edge's actual children and retains that edge through setChildren, including its constraint. Different edges with the same parts, root symbol and child shapes can share split computation without sharing their children or constraint payloads.

PreparedTemplate equality, order and hash use catalog identifiers. This is sound within one catalog, where equal identifiers name equal structural parts. The new memo is inside the same refine application that captures originalTemplate and preparedChildren for that catalog. It is not a top-level TypeableMemoCache shared by unrelated exclusions. No cross-catalog identifier alias is introduced.

Lifetime, purity and strictness

memo allocates a private table for the evaluated function application. exclude keeps one refined closure for its prepared catalog, so walk and copiesOf share tables across that exclusion's recursive work and repeated uses of the retained exclusion function. The table does not evict. Keys and split results remain reachable while the function or retained computations keep that table alive. The new table can retain more shape and obligation data than the old walk-only memo. This is a real allocation tradeoff, not a new process-wide catalog registry.

The existing cache uses hash-map key equality, so a hash collision does not identify different keys. Atomic insertion keeps the first lazy value. Concurrent duplicate computation can occur but both computations call the same pure edgeCopiesWith function. No IO-dependent callback, mutable solver result, native enumeration state or changing environment is read by that function. The cache implementation is unchanged.

Hashing the key can demand the full child-shape lists earlier than the old edgeCopiesWith call did. That call could reject some wanted root parts before inspecting all shapes. On the intended total finite templates and valid finite interned graph representation, this adds exposure/hashing work and can retain more data; it does not change the computed split lists. This review does not claim identical lazy forcing, behavior on bottom/invalid open graphs, or a universal speedup. The changelog's 3.8% HugeLists measurement is an upstream historical claim. The retained integration tests do not independently measure that workload.
