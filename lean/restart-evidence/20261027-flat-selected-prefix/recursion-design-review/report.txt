Cache correctness trap

Do NOT apply FlatNativeIndex.write_correct to frame checked before with lost=originalScs: checked.values[uv] is already pending(handle,[]) and its stored references are empty. That theorem requires the supplied lost list to equal the actual old stored references. Apply correctness at the PRE-clear resolved cache where the bucket is originalScs, using the actual write, or transfer the original producer's returned CacheValid through final Related via correct_of_related. The adapter still executes its count calculation at checked representatives; the actual setValue leaves that forest equal to resolved, as proved in old adapt_after_write. These are compatible statements, not a license to count at an arbitrary original forest.

Ready ensures that selected uv is its actual representative and that the raw slot is in range. A standalone adapter at an arbitrary nonroot uv need not produce valid flags for the root cleared by checkRepeated. The genuine selected producer supplies Ready from initial Safe, CacheValid and pure selection. Do not add a new caller-supplied desired cache or final Safe premise. Frame alone does not imply Safe. The old producer returns Safe at the actual endpoint. Caller/native heap/queries and metadata stay unchanged by this read/clear/restart boundary. Canonical or assignment semantics are separate conclusions and are not needed to state runtime correspondence.
