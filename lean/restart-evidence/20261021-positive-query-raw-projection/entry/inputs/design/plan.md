## Why use the existing Required receipt

The receipt supplies prepared Ready, admission, Values and domains.
Its stability field supplies the literal call used by the public corridor producer.
Both fields are indexed by the SAME prepared values and heap.
The receipt does not supply the desired raw corridor conclusion.
There is no redundant literal equation argument.
The proof does not infer identity of fuel-indexed execution proofs.
It only uses the actual completed equality supplied by that receipt at sufficient bounds.

A stronger alternative can remove the Required receipt premise.
It would take Ready, admission, Values and proper selected paths at the original entry.
It would call `ConjunctionRequired.required_complete`, compare the produced return with a supplied literal equation using `required_unique`, and then use the same adapter route.
This repeats an access pattern already implemented by `ConjunctionRequiredActual.verified` and adds Scan-facing parameters.
It is unnecessary for the requested concrete pipeline integration.

## Limits

The ordered relation starts at preparedValues and ends at the actual class result.
It does not identify originalValues with preparedValues or with any later phaseValues.
It does not transport a false gate onto changed captures.
It supplies finite raw endpoint corridors, not positive ancestry, original source Paths, or a whole-value cap for unrelated branches.
It does not supply native/Merge warm laws from current physical availability.
It does not cover an internal failing class/Parent instruction or prove outer completion.
