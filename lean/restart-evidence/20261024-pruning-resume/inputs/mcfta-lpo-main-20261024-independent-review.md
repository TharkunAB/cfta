The earlier comparator probe remains useful: its GT/LT output is expected even after this repair. The new regression must check rewrite/pruning behavior, rather than require the comparator reversal to disappear.

## Scope and contracts

- Ground LPO now compares the program structure using erased equality. Raw `Term` comparison remains the fallback. On the intended well-formed annotated applicative program domain, the intended proof is that distinct erased programs are comparable by the erased LPO, leaving raw comparison only as the annotation tie-break. The code comment's transitivity assertion is not a proof for every raw or malformed `Term`.
- The rewrite traversal keeps outermost/leftmost priority and both oriented/unoriented candidate checks. Function descent composes the complete consecutive application spine for PathOrder. Argument descent resets that context; its whole-term decrease still relies on argument-position compatibility of the order. KnuthBendix uses `id` as before. The KBO order and its template admissibility are unchanged because its `appliedGreater` returns True.
- `appliedGreater` tests one shared synthetic argument for a function-typed side, or a type-variable side. It returns True for a side whose type cannot take an argument. A general correctness lemma must justify the one-argument criterion for every admissible additional argument and longer spine, under term/type substitution and ranked variables. It must also justify the synthetic `<v>applied`/`<t>applied` freshness convention on the actual rule-input domain; the code chooses fixed names rather than checking freshness. No new concrete collision or runtime defect is claimed by this review.
- Unsafe one-way orientation now falls back to retaining both directions in the existing unoriented/nonRewriting indexes. Individual rewrites still test the instantiated order. This may change completion work and representative laws; it is not an extra equation-validity check.
- Template production is more conservative for PathOrder. This repairs the specific application-context witness only if the rule itself is valid and the other typing, substitution, linearity and annotation-encoding requirements hold. It does not prove that every emitted template safely removes a program, that partial matches can prune, or that compiled and oracle pruning have the same language.
- The README now counts 8 separate validation cases, 40 boundary cases and 16 predicate cases: 64 cases in addition to the requested random count. This matches the unchanged `testSchedule` (Types.hs1169–1181: 8*4 + 2*4 boundary, 8*2 predicate). It repairs the earlier documentation undercount; this commit does not add those cases or make finite testing a law proof.
